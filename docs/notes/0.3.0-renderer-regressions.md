# Lantern 0.3.0 Renderer Regression Notes

> **Applies to:** automatic 3D and Three.js's forced WebGL 2 backend
>
> **Authority:** presentation only; simulation physics, particles, schema v4, recordings, and replay are unchanged

This note preserves the two first-use failures found while stabilizing 0.3.0. Keep the symptoms and invariants here even if the implementation changes, because both defects were easy to mask with warmed runs or percentile-only metrics.

## Cold shader and pipeline stalls

### Symptom

The first projectile, explosion, and final particle teardown produced isolated stalls. Warmed shots were substantially smoother, and percentile summaries could hide the single worst frame.

### Causes

- Inactive point lights became renderer-invisible, changing the compiled light topology as fire effects appeared and disappeared.
- The 4,096-entry particle color attribute was allocated lazily on the first explosion.
- Frame spacing was recorded only after the 250 ms simulation clamp, obscuring raw wall-clock stalls.

### Required invariants

- All eight point-light objects remain scene-resident and renderer-visible for the 3D presentation lifetime. Inactive lights use intensity zero and never cast shadows.
- Full-capacity instance matrices and instance colors are allocated before gameplay. Particle and rock colors use dynamic draw usage.
- Empty pools use draw count zero without clearing or reallocating their backing arrays.
- The initial map, floor, walls, rocks, projectiles, particles, markers, default materials, and resident eight-light topology are built before `compileAsync()`.
- Fixed-step runtime and input begin only after default 3D compilation succeeds.
- Raw request-animation-frame spacing and bounded presentation phases retain last/p50/p95/p99/max plus recent spikes.

Bloom and shadows remain intentional opt-in cold paths in 0.3.0.

## Stale particle locations on reused instance slots

### Symptom

For one frame, a new impact could reveal the final positions of an earlier explosion. The empty-to-active guard fixed isolated shots, but rapid impacts still reproduced the artifact whenever a second burst arrived while an earlier spark shower remained active. Resetting simulation did not replace the renderer buffer, so it did not eliminate the underlying reuse condition.

### Root condition

The active particle prefix grew in the same renderer submission that refreshed newly exposed matrix/color slots. Those tail slots retained earlier GPU-visible transforms until the refreshed prefix was safely submitted. Guarding only `0 -> active` missed `active -> larger active` transitions from overlapping explosions.

### Required invariant

Every increase in particle draw count is deferred for one renderer submission:

```text
previous safe draw count = N
new logical particle count = M, where M > N

write and mark matrix/color range 0..M
render only the previously submitted prefix 0..N
after submission, permit draw count M on the next frame
```

Existing sparks remain visible during that upload. If the pool is empty, it remains allocated but hidden at draw count zero. No gameplay state, particle behavior, or recording data is changed.

### Manual reproduction

1. Use the 3D route and fire two fireballs rapidly toward visibly separated walls.
2. Before their combined shower finishes, fire two more toward different locations.
3. Watch the earlier impact locations as the later pair collides.
4. Repeat after **Reset**, and repeat with `?renderer=3d&backend=webgl`.

Acceptance requires no one-frame flash at any earlier impact location. A newly added particle batch may become drawable one frame after its data upload.

## Diagnostic workflow

- Call `window.__lantern.resetPerformanceMetrics()` before a cold or warmed comparison; it does not reset simulation or renderer caches.
- Use `window.__lantern.presentation()` for warmup state, resident/active lights, phase summaries, and recent spike transitions.
- Correlate raw frame maximum with presentation `updateMs`, `lightsMs`, and `submitMs`; do not rely on percentile summaries alone.
- Keep Canvas2D available as the presentation oracle. If the snapshot is correct there and only 3D flashes, investigate the presentation pool before changing simulation.
