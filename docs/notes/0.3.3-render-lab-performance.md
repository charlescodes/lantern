# Lantern 0.3.3 Effect-Local Lighting and Render Lab

> **Authority:** presentation only
>
> **Compatibility:** simulation truth, schema v4, scenario v2, command recordings, replay behavior, and the Canvas2D default route are unchanged

## Effect-local light topology

The Balanced 3D route creates 16 resident point lights during startup. Supported
fixed capacities are 8, 16, 32, and 64; each is compiled during warmup and
requires a reload to change. Every resident remains scene-visible,
non-shadow-casting, and inactive at intensity zero when it has no assignment.

Each fireball owns one atomic eight-slot presentation group:

- Slot 0 follows the projectile and keeps the same resident identity when it
  becomes the explosion pulse.
- Slots 1–7 lease the seven largest newly observed sparks associated with that
  impact. Maximum spawned size ranks first, then current-size/life score, then
  particle ID.
- Newly observed particles associate with the nearest newly observed explosion
  origin; equal distances prefer the lower event ID. Direct particle fixtures
  use a deterministic orphan tail group.
- Leases never backfill. A carrier disappearance leaves its exact slot dark.
  Whole-group eviction permanently retires an impacted tail; an unlit flight
  may request a fresh group when that projectile impacts.
- Admission compares most-recent effect tick, then impact, flight, and tail
  phase, then ID. Capacity is allocated or evicted only in whole eight-slot
  groups.

The existing smooth pulse and spark fade remains. One fireball therefore uses
at most eight active lights during its pulse and at most seven afterward.

Simulation seed plus projectile ID selects a stable red, green, or blue bias and
a 1–3% mix amount. Rec.709 luminance is restored after mixing so the variation
does not become a brightness change. All lights in one fireball group share the
same tint. Mesh materials keep their original fire colors, and
`lightColorVariation` can be toggled live.

## URL settings and Render Lab

Canvas2D remains the no-parameter default. Balanced 3D is:

```text
?renderer=3d&lights=16&dpr=1.5&aa=1
```

The complete bounded setting surface is:

| Setting | Values | Application |
| --- | --- | --- |
| `renderer` | `2d`, `3d` | Reload |
| `backend` | automatic when absent, `webgl` | Reload |
| `lights` | `8`, `16`, `32`, `64` | Reload |
| `aa` | `0`, `1` | Reload |
| `dpr` | `1`, `1.5`, `2` | Live |
| `dynamicLights` | `0`, `1` | Live |
| `lightColorVariation` | `0`, `1` | Live |
| `bloom` | `0`, `1` | Live |
| `shadows` | `0`, `1` | Live |

Invalid values fall back independently to Balanced defaults. The URL is the
sole persisted state; there is no hidden `localStorage` copy.

Render Lab exists before asynchronous renderer initialization. It remains
usable if initialization or shader compilation fails and offers direct
recovery routes to the next lower light tier, forced WebGL 2, and Canvas2D.
Its live instrument reports the active backend, CSS and backing resolution,
effective DPR, active/resident light counts, frame timing, renderer and
presentation CPU timing, and GPU timestamp availability.

## Ten-second performance reports

A capture resets timing histories, leaves gameplay unscripted, and observes the
ordinary render path for ten seconds. The JSON report contains:

- browser, device, viewport, screen, connection, DPR, and secure-context facts;
- renderer and visual settings;
- maximum projectiles, particles, rocks, contacts, and active/resident lights;
- frame, simulation, snapshot, renderer CPU, and presentation-phase timings;
- warmup, draw, triangle, group, spike, and light summaries;
- GPU render percentiles when timestamp queries are available, otherwise
  `gpuRenderMs: null`.

GPU queries are enabled only for the active capture. The panel can copy or
download the latest report; the probe exposes the same asynchronous capture
and latest-report retrieval.

## LAN and support policy

Run:

```bash
npm start -- --host 0.0.0.0
```

An optional `--port` overrides port 4173. `HOST` and `PORT` remain compatible.
The server enumerates LAN IPv4 interfaces and prints Canvas2D, automatic 3D,
and forced-WebGL 2 phone routes. It serves files without authentication, so use
only a trusted network. Each device runs an independent simulation; this is not
a multiplayer server.

Raw LAN HTTP is not a secure context, while same-device loopback is potentially
trustworthy. Phone testing over this workflow therefore targets forced WebGL 2;
phone WebGPU awaits an HTTPS workflow. Three.js's `WebGPURenderer` continues to
select WebGPU where available and automatically fall back to WebGL 2.

Current 3D support is defined by a maintained browser/OS, hardware-accelerated
WebGL 2, and passing the Low capture threshold. No minimum GPU model is declared
yet. The Windows 7 ThinkPad is test-only legacy evidence: use forced WebGL 2 and
Low settings, and do not make release acceptance depend on it. Chrome 109 was
the final Windows 7 Chrome, while Firefox 115 ESR is the final Firefox branch
for Windows 7/8/8.1.

Current mobile WebGPU evidence includes supported Android 12+ devices in recent
Chrome and Safari 26 on iOS/iPadOS 26. Unsupported or insecure-context devices
use WebGL 2 fallback.

## Acceptance thresholds

Low (`8` lights, `1×` DPR, AA off) must reach median 30 FPS, frame p95 at or
below 40 ms, and presentation CPU p99 below 8 ms. Balanced and higher tiers
target median 55 FPS, frame p95 at or below 22 ms, and presentation CPU p99
below 8 ms on intended hardware.

Browser acceptance covers automatic WebGPU, forced WebGL 2, Canvas2D recovery,
all resident capacities, two independent rapid impacts, oldest-tail eviction on
a third, subtle tint, responsive phone controls, LAN capture, and the optional
ThinkPad run.
